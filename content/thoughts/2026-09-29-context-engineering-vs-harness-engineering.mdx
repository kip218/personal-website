I kept hearing the terms "context engineering" and "harness engineering" thrown around. I didn't fully understand the distinction until I started building a PR review bot for my team. 

Our existing PR review cycle had a couple bottlenecks as it relied on senior engineers being available to review tickets before they were approved. We'd have several PR reviews sitting in a queue in the dedicated PR review Slack channel until the senior engineer had time to review it. Based on this pain point, I decided to build a Slack bot that gives instant feedback once the ticket is posted in the channel.

With the PR review bot, the review cycle now looks like this:
1. An engineer posts the ticket requiring PR approval in our Slack channel.
2. The bot takes the ticket URL, pulling in the necessary context: the draft, the code changes, ETL configs, and everything else related to the PR. The bot runs a classifier agent that identifies what type of ticket it is and which review agents to dispatch.
3. Each review agent specializes in something specific: SQL logic, ETL patterns, QA validation, process compliance. They run independently in parallel, each agent tightly scoped to specifically keep it focused and minimize context bloat.
4. Once each review agent finishes, a reconciler agent collects all the results, deduplicates issues and assigns severity to each of them - critical, warning, or note - and posts a final structured review in the Slack thread with a verdict on whether the PR is ready to approve or not.

The first version of this bot was a single Claude skill with a fixed prompt. It worked, but its output was generic. It didn't know about our proprietary config tables, our team's naming conventions, or how our ETL pipelines are structured because it was missing specific context on how *our* team pushes updates and reviews tickets.

So then I started building the context layer - our internal documentation on our team's review standards, domain knowledge, and conventions. Together with team leads and other senior engineers, we made a Notion knowledgebase built specifically for Claude. These pages were indexed and synced automatically to the repo whenever I merge to main on Github. The key point about this context layer is that each review agent only gets fed the Notion pages relevant for its specific review purpose. The SQL review agent gets our SQL standards and the ETL review agent gets our pipeline conventions. This keeps each review agent scoped tightly and reduces context bloat - I noticed that this reduced the rate of hallucination and increased consistency in the review results.

The context layer made the reviews better, but I still had a problem: how do I keep improving the bot without manually reviewing every single output in the PR channel? At first I started off reviewing the output manually and refining each agent prompt and the knowledgebase, but I quickly realized this was not scalable nor efficient. I was becoming the bottleneck for the bot's improvement cycle. So I found a better way to structure the feedback loop. For each review posted by the bot, the engineer doing the manual review can react with a thumbs up or thumbs down, which helped me filter out the good reviews from the bad, so that I could tweak the review prompts based on the "bad" reviews.

But this wasn't enough - there was still too much manual work on my end. I started tracking the full Slack thread for each PR - if someone writes in the thread "the bot flagged this but it's not relevant for this type of update", or "the bot missed this config issue", I could use this as a more detailed signal to improve the review agent prompts. All of this feedback gets stored in BigQuery, and every week, the bot sends me a summary report listing suggested refinements to each review agent's prompt based on the additional context collected from each PR's Slack thread. I still go through each suggestion manually to make sure it's not just suggesting additional rules and creating unnecessary bloat in the review prompts, but the value in this feedback system is that I don't need to spend manual hours sifting through each review and locating which review prompt is responsible for the wrong output. The improvement cycle went from my reading every output to a system that funnels the right feedback to me directly.

Going back to my first point - this is when I really started understanding the concept of context engineering vs harness engineering. The context layer is what each agent sees during a review - the ticket content, the code changes within it, and the additional knowledge being fed into the context. The harness is the whole system at a higher level - the classifier, the reconciler, the feedback pipeline, the weekly digest. It's the system that decides how the context layer gets constructed for each PR, how each output gets validated, and how it improves over time.

I don't really have a moral of the story to finish out this post - I'm just writing down my thoughts here. Though if there is a takeaway, it'd be to start building things. Especially when you hear a concept that is hard to fully internalize by just reading about it. Try building something practical that makes use of those concepts - I'm sure it will help you get a better feel for what those flashy new buzzwords mean.
